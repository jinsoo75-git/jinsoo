# 00. Overview

## 프로젝트 한 줄 소개

**TaskFlow Pro** — 팀 업무 관리 풀스택 웹 앱

## 문서 지도

| 파일명 | 역할 | 여기서 알 수 있는 것 |
|---|---|---|
| `00-overview.md` | 전체 안내 | 프로젝트 개요, 문서 읽는 순서, 문서 구조를 나누는 이유 |
| `01-product.md` | 제품 정의 | 무엇을 만드는지, 누구를 위한 것인지, 핵심 사용자 시나리오 |
| `02-specs.md` | 기능 명세 | 각 기능의 상세 동작, 입출력, 예외 케이스 |
| `03-design.md` | 아키텍처/디자인 | 시스템 구조, 폴더 구조, 데이터 모델, API 설계 |
| `04-tasks.md` | 작업 목록 | 구현할 작업 단위, 우선순위, 진행 상황 |
| `05-conventions.md` | 컨벤션 | 코딩 스타일, 네이밍, 커밋 메시지, 테스트 규칙 |

## 읽는 순서

```
00-overview → 01-product → 02-specs → 03-design → 04-tasks → 05-conventions
```

작업을 시작하기 전 이 순서대로 모든 문서를 읽는다. 순서를 건너뛰거나 역순으로 읽지 않는다.

## 왜 이렇게 나누는가 — 관심사 분리(Separation of Concerns)

각 문서는 하나의 질문에만 답하도록 나뉘어 있다. 하나의 문서가 "무엇을/왜/어떻게/무엇부터/어떤 규칙으로"를 동시에 다루면, 문서가 커질수록 특정 정보를 찾기 어렵고 수정 시 다른 관심사까지 함께 건드리게 된다.

- **왜(Why) — `01-product.md`**: 제품의 목적과 사용자 문제. 기능 구현 방법이 바뀌어도 이 문서는 거의 바뀌지 않는다.
- **무엇을(What) — `02-specs.md`**: 기능의 정확한 동작 규약. 제품 목적은 그대로여도 세부 명세는 자주 갱신된다.
- **어떻게(How) — `03-design.md`**: 기술적 구현 구조. 명세를 만족시키는 방법은 여러 가지일 수 있으므로 명세와 분리한다.
- **무엇부터(What's next) — `04-tasks.md`**: 설계를 실제 작업 단위로 쪼갠 것. 설계는 안정적이어도 작업 순서/우선순위는 매일 바뀔 수 있다.
- **어떤 규칙으로(Rules) — `05-conventions.md`**: 프로젝트 전반에 적용되는 스타일 규칙. 특정 기능이나 설계와 무관하게 독립적으로 존재한다.

이렇게 분리하면 각 문서를 독립적으로 갱신할 수 있고, 특정 정보(예: 커밋 규칙)를 찾을 때 전체 문서를 뒤지지 않고 바로 해당 파일만 확인하면 된다. 이는 코드에서 관심사를 모듈별로 분리하는 것과 동일한 원칙이다.
